# Handling Imbalanced Datasets — Senior ML Engineer Interview Prep (2026)

> Pairs with folder 20 (evaluation). This doc covers the actual techniques for *training* a good model under class imbalance, and how the field's thinking on SMOTE specifically has shifted by 2025–2026.

## TL;DR Refresher

- **Resampling**: random oversampling (duplicate minority examples — risks overfitting to duplicates), random undersampling (drop majority examples — risks losing useful information), **SMOTE** (Synthetic Minority Oversampling Technique — generates synthetic minority examples by interpolating between a minority point and its nearest minority neighbors) and its variants (Borderline-SMOTE, ADASYN).
- **Algorithm-level**: class-weighting (penalize misclassifying the minority class more heavily in the loss — supported natively by most sklearn estimators, XGBoost/LightGBM/CatBoost via `scale_pos_weight`/`class_weight`), threshold tuning (adjust the decision threshold post-training rather than resampling at all), and cost-sensitive learning (directly encode business misclassification costs into the loss).
- **Loss-level**: Focal loss (down-weights well-classified "easy" examples, forcing the model to focus learning capacity on hard/minority examples) — originally from object detection, now widely applied to tabular/general imbalanced classification.

## What's New / State of the Art (2025–2026)

- **"Beyond SMOTE" is now a distinct, common framing in 2025–2026 practitioner writeups** — a growing body of applied evidence and critique argues that SMOTE's naive linear interpolation between minority neighbors can generate unrealistic synthetic points (especially in high-dimensional or noisy feature space, and especially poorly suited to sparse text/NLP feature spaces), and that in many cases **class-weighting or simply adjusting the decision threshold outperforms SMOTE with less complexity and no synthetic-data risk** ([Handling Imbalanced Classification: What Works Better Than SMOTE, 2026](https://www.analyticsvidhya.com/blog/2026/07/class-imbalance-ml/), [Beyond SMOTE: Pragmatic Techniques for Imbalanced Text Datasets](https://medium.com/@amolborkar27/beyond-smote-pragmatic-techniques-for-imbalanced-text-datasets-00c81679bea6)). A senior candidate in 2026 should present SMOTE as *one tool among several*, not the default first move.
- **Cluster-based and noise-reduced SMOTE variants** (e.g., Cluster-Based Reduced Noise SMOTE) remain an active 2025 research area specifically addressing SMOTE's tendency to generate synthetic points in noisy/overlapping regions between classes — worth naming as evidence the field is still refining rather than abandoning SMOTE outright ([Cluster-Based Reduced Noise SMOTE, PMC 2025](https://pmc.ncbi.nlm.nih.gov/articles/PMC11809912/)).
- **Focal loss continues to gain adoption outside its original computer-vision/object-detection context** — 2025 papers apply enhanced/adaptive focal loss variants to tabular fraud detection and other structured-data imbalance problems, often combined with explainability requirements (e.g., an explainable-AI-compatible focal loss for insurance fraud detection) — a sign that loss-function-level solutions are increasingly preferred over data-level resampling in regulated domains where synthetic data raises auditability questions ([Enhanced Focal Loss for Auto Insurance Fraud Detection with XAI, arXiv 2025](https://arxiv.org/html/2508.02283v1)).
- **The default 2025–2026 senior recommendation order** has shifted toward: (1) try class-weighting and threshold tuning first (cheap, no synthetic data, easy to reason about), (2) try focal loss or cost-sensitive loss if the model architecture supports custom losses, (3) reach for SMOTE/resampling only if the above are insufficient, with careful cross-validation-safe application (resample only inside the training fold, never before the train/test split).

## Senior-Level Interview Questions

**Q1. Walk through exactly how SMOTE generates a synthetic example, and identify a scenario where this generation process actively hurts the model.**
Strong answer: For a minority-class point `x`, SMOTE finds its `k` nearest minority-class neighbors, picks one (`x_nn`) at random, and generates a synthetic point `x_new = x + λ·(x_nn - x)` for random `λ ∈ [0,1]` — a point linearly interpolated between the two. This actively hurts the model when the minority class isn't linearly "between" its neighbors in a meaningful way — e.g., in sparse, high-dimensional one-hot/text feature space, the interpolated point may not correspond to any realistic/valid data point at all (a linear blend of two sparse binary vectors isn't itself a valid sparse binary vector), or when minority points near the class boundary get interpolated *into* the majority class's region, amplifying label noise rather than useful signal.

**Q2. You have a choice between SMOTE-oversampling before training vs. class-weighting during training. Give the strongest argument for each, and state which you'd default to.**
Strong answer: SMOTE's case: it changes the actual training data the model sees, which can help models/losses that don't natively support per-class weighting, and can sometimes help the model learn a richer minority-class decision region rather than just penalizing errors more. Class-weighting's case: it doesn't fabricate any data (no synthetic-data validity risk), is computationally cheaper (no synthetic-sample generation step), directly and transparently encodes the cost asymmetry into the loss function, and is trivially auditable (no question of "is this synthetic point realistic"). Default in 2025–2026 practice: start with class-weighting/threshold-tuning as the simpler, safer baseline, and only add resampling if class-weighting alone is measurably insufficient — a defensible, current-best-practice answer.

**Q3. Explain focal loss mathematically and why it helps with class imbalance differently than simple class-weighting.**
Strong answer: Standard cross-entropy is `-log(pₜ)` where `pₜ` is the model's predicted probability for the true class; focal loss modifies this to `-(1-pₜ)^γ · log(pₜ)`, adding a modulating factor that down-weights the loss contribution from already-well-classified examples (`pₜ` close to 1 → `(1-pₜ)^γ` close to 0) while leaving hard/misclassified examples' loss largely unchanged. This differs from class-weighting (which applies a fixed multiplier per class regardless of how confidently each individual example is classified) by adapting *per-example*, based on classification difficulty, not just class membership — useful when the majority class itself contains a mix of easy and hard examples and you want the model to keep focusing on genuinely hard cases as training progresses, not just rebalance the aggregate class contribution.

**Q4. A teammate applies SMOTE to the entire dataset, then does a train/test split. What's wrong with this, and what's the correct procedure?**
Strong answer: This leaks information — synthetic minority points generated using neighbors that may end up in the test set (or that are themselves near-duplicates of test-set points, since SMOTE interpolates from real data points) can end up in the training set, giving the model indirect access to test-set-adjacent information and inflating evaluation metrics unrealistically. Correct procedure: split into train/test (or CV folds) *first*, then apply SMOTE only within each training fold, never touching the test/validation set, which must always reflect the true, unmodified class distribution (consistent with the evaluation doc's guidance).

**Q5. Design an end-to-end strategy for a severely imbalanced (0.05% positive rate) real-time fraud-scoring system, covering both training and evaluation.**
Strong answer: Training — start with class-weighting (`scale_pos_weight` in XGBoost/LightGBM, calibrated to roughly the inverse class ratio as a starting point, then tuned via validation performance) combined with a gradient-boosted model (naturally handles imbalance reasonably well with weighting); consider focal loss if using a neural architecture; avoid heavy oversampling at this extreme ratio (huge synthetic-to-real ratio risk). Evaluation — PR-AUC as the primary ranking metric (per folder 20), calibration-aware threshold tuning against an explicit cost matrix (false-negative fraud cost vs. false-positive customer-friction cost), and continuous production monitoring of precision/recall drift as fraud patterns evolve (concept drift is common and severe in fraud domains) — tie this back to periodic retraining triggers rather than a one-time static threshold.

## Common Pitfalls & Follow-Up Probes

- Treating SMOTE as the default/only answer to "how do you handle imbalance" — 2025–2026 senior answers should present a menu and justify the choice.
- Applying SMOTE (or any resampling) before the train/test split, or across cross-validation folds instead of within each fold — a classic, serious leakage bug.
- Forgetting that resampling changes the training distribution but the model's raw output probabilities must often be corrected (offset/recalibrated) to reflect the true population's base rate before being used as real probabilities in production (directly relevant if combining with the calibration discussion in folder 20/24).
