# Feature Engineering — Senior ML Engineer Interview Prep (2026)

> The 2025–2026 update here is substantial: LLMs have become active participants in feature engineering, not just consumers of engineered features. This doc covers both classic technique and the new LLM-assisted workflow.

## TL;DR Refresher

- Classic techniques: encoding categoricals (one-hot, target/mean encoding, ordinal), binning/discretization, polynomial/interaction terms, date/time decomposition (day-of-week, cyclical encoding via sin/cos), aggregation features (group-by statistics, rolling windows for time series), domain-specific transforms (log/Box-Cox for skewed data).
- **Target/mean encoding requires leakage protection** — analogous to CatBoost's Ordered TS (folder 13): naive target encoding on the full training set leaks label information; the correct approach uses out-of-fold or ordered/smoothed encoding.
- Feature engineering quality is frequently the single biggest lever on tabular-model performance — more impactful than algorithm choice or hyperparameter tuning in many real-world problems, a point worth making proactively in interviews.

## What's New / State of the Art (2025–2026)

- **LLM-assisted/automated feature engineering is a genuinely new and fast-moving 2025–2026 research and applied area.** Systems like **LLM-FE** use large language models as evolutionary optimizers — proposing candidate feature transformations in natural language/code, evaluating them against a downstream model's performance, and iterating — essentially automating the "try a log transform, try an interaction term" trial-and-error process a human engineer would do, guided by the LLM's prior knowledge of domain-relevant transformations ([LLM-FE, arXiv:2503.14434](https://arxiv.org/abs/2503.14434), [TMLR 2026](https://mlanthology.org/tmlr/2026/abhyankar2026tmlr-llmfe/)).
- **Human-LLM collaborative feature engineering** is emerging as the practical middle ground in 2025–2026 production settings — rather than fully automated feature generation, teams use LLMs to *propose* candidate features/transformations from domain knowledge and documentation (which a human then reviews, validates for leakage, and approves), speeding up the ideation phase while keeping a human in the loop for correctness and leakage review ([Human-LLM Collaborative Feature Engineering, 2026](https://awesomepapers.io/recommender-systems/papers/2601.21060)).
- **LLM-guided feature engineering for time series with explicit temporal-leakage control** is a notable 2025–2026 research direction specifically addressing the risk that naive automated feature generation (including LLM-driven) can silently introduce future-information leakage in time-series contexts — a senior candidate should flag this risk explicitly whenever LLM-assisted feature engineering is discussed for temporal data ([LLM-Guided Automated Feature Engineering for Time Series with Temporal Leakage Control](https://doi.org/10.3390/ai7070245)).
- **Feature stores as standard infrastructure**, not a nice-to-have — by 2025–2026 most mature ML orgs have converged on feature stores (Feast, Tecton, or in-house equivalents) specifically to solve the train/serve consistency problem for engineered features (the same feature-engineering pipeline/code must run identically at training and serving time) — this infrastructure point is now a standard senior "how would you productionize this" follow-up.

## Senior-Level Interview Questions

**Q1. Explain target/mean encoding and precisely how it leaks label information if done naively — then describe the correct, leakage-safe procedure.**
Strong answer: Naive target encoding replaces each category with the mean target value computed over the *entire* training set for that category, including the row being encoded — so a row's own label directly influences its own feature value, and the model can essentially "read off" a noisy version of the answer, especially damaging for low-cardinality-count categories where a single row's label swings the category mean substantially. Correct procedure: use out-of-fold encoding (compute each row's category encoding using only the *other* folds' data, cycling through k-fold CV) or an ordered/permutation-based approach analogous to CatBoost's Ordered TS (folder 13); additionally apply smoothing (blend the category mean with the global mean, weighted by category sample count) to stabilize encoding for rare categories.

**Q2. Design an LLM-assisted feature engineering workflow for a tabular churn-prediction problem, and describe your leakage-review process.**
Strong answer: Feed the LLM the feature schema, sample rows, and domain context (e.g., "telecom churn, these are billing/usage columns"), ask it to propose candidate derived features (ratios, interactions, domain-specific transforms like "days since last high-usage month") with natural-language justification for each; evaluate each candidate's incremental contribution via a quick model-performance check (e.g., feature importance or ablation on a validation set) rather than trusting the LLM's proposal blindly. Critically, every proposed feature — LLM-generated or not — goes through the same leakage review as human-engineered features: check that it's computable using only information available *at prediction time* (not, e.g., using a "total contract value" that implicitly includes future months), which is exactly the failure mode the temporal-leakage-control research explicitly targets for time-series-adjacent features.

**Q3. Cyclical time features (hour-of-day, day-of-week) — why does naive integer encoding hurt model performance, and how do you fix it?**
Strong answer: Encoding hour-of-day as a raw integer 0–23 implies hour 23 and hour 0 are maximally *far apart* numerically, when they're actually adjacent in real time (11pm and midnight are one hour apart, not 23) — this false discontinuity misleads distance-based and even some tree-based/linear models about the feature's true topology. Fix: cyclical encoding via `sin(2π·hour/24)` and `cos(2π·hour/24)` as two features — this maps the 24-hour cycle onto a circle, correctly placing hour 23 and hour 0 close together in the resulting 2D representation, preserving the true cyclical adjacency structure.

**Q4. A gradient-boosting model's feature importance shows a newly engineered "account_age_at_prediction_time" feature as by far the most predictive signal for churn. How do you investigate before trusting this?**
Strong answer: Extremely high, suspiciously dominant importance for a single engineered feature is a classic leakage red flag — investigate whether "prediction_time" in the feature's computation is genuinely the actual inference-time cutoff, or whether it was inadvertently computed using data from after the label's observation window (e.g., using the account's *current* age at training-data-collection time rather than the age as of each historical prediction point) — walk through the feature's exact computation logic against the label's time window explicitly, and check whether the feature's predictive power holds up on a genuinely time-forward validation split (train on older data, validate on strictly later data) rather than a random split, which is the strongest practical test for this class of temporal leakage.

**Q5. How do you decide when manual/expert feature engineering is worth the investment versus letting a model (e.g., gradient boosting, which handles some interactions natively, or a foundation model) learn representations automatically?**
Strong answer: Manual feature engineering is most worth the investment when you have strong domain knowledge the model can't easily discover from raw data alone (e.g., a ratio or domain formula that's non-obvious from the raw columns, or aggregating information across a time window in a way gradient boosting's per-row splits can't natively express), or when interpretability requires human-understandable engineered features rather than opaque learned representations. It's less worth heavy investment when using models that already handle a lot of this automatically (gradient boosting captures many interactions and non-linearities via tree splits without explicit feature engineering; tabular foundation models and LLM-assisted pipelines are increasingly automating the ideation step too) — in 2025–2026 practice, the highest-leverage manual effort tends to concentrate on domain-specific features a general-purpose method genuinely can't infer from the data alone (e.g., business-rule-derived features, external data joins), while leaving generic interactions/transforms to the model or to LLM-assisted generation with human leakage review.

## Common Pitfalls & Follow-Up Probes

- Not being able to name a concrete leakage-detection procedure (time-forward validation split, ablation, computation-logic audit) when a feature looks "too good."
- Treating LLM-assisted feature engineering as fully automatic/trustworthy without describing a human review step for leakage and correctness.
- Forgetting that feature engineering must be implemented identically (ideally the *same code*) at training and serving time — a frequent, costly train/serve skew source (see the Distances & Feature Scaling doc for the general pattern).
